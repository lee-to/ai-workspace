# Pin hosted cache privacy and exercise cloud failure boundaries

**Date:** 2026-08-25 22:39 MSK
**Files:** src/cloud/mcp.rs, src/cloud/client.rs, src/cloud/http.rs, src/cloud/store.rs
**Severity:** high

## Problem

Hosted MCP discovery and tool-list responses advertised the non-schema value `workspace` for `cacheScope`. Cloud tests also left client status/response limits and snapshot retry, conflict, force, and concurrency behavior uncovered.

## Root Cause

The protocol result metadata was checked for presence but not validated against the selected MCP schema's enum. Cloud happy-path tests proved basic connectivity without exercising the implemented trust-boundary branches.

## Solution

- Set both hosted MCP cache scopes to `private` and assert the value in unit and authenticated HTTP tests.
- Cover actionable 401, 403, 413, 429, and 5xx client errors plus the bounded response body and unchanged local state.
- Exercise identical retries, stale conflicts, forced overwrites with audit fields, and serialized concurrent first/revision pushes against PostgreSQL.
- Reuse existing safe `[FIX:cloud-protocol]` and cloud request/store logging; no tokens or response bodies are logged.

## Prevention

- Assert protocol enum values, not only field presence.
- Every network/storage limit or conflict branch needs one runnable boundary check.
- Run PostgreSQL-gated tests with the restricted runtime role so early-return tests cannot mask missing coverage.
